# 知研——产品设计文档（v4.2）

> 版本：v4.2  
> 日期：2026-09-02  
> 状态：已确认的 MVP 体验修复规格；实施仍受仓库质量门禁与真实服务门禁约束  
> 前序版本：[v4.1](./2026-09-01-zhiyan-design-v4.1.md)

---

## 0. 文档目的

v4.2 在 v4.1 的产品定位、长期蓝图和 M1 路线不变的前提下，修复当前 MVP 主链路中五项影响体验与可信度的问题：

1. 热榜数据不能稳定、诚实地显示；
2. 报告未能清楚表达多个观点及其依据；
3. 对话历史和用户即时输入不可见；
4. 刘看山反馈没有正确反映真实请求状态；
5. 诘问过于固定、过强，不能像老师一样先回应再引导。

本版本是对 MVP 核心体验的收束，不新增快速、深度、趣味、GalGame、知识库或账户模式。v4.1 中关于 M1、平台、迁移、隐私和真实服务的门禁继续有效；本文不构成绕过这些门禁的授权。

### 0.1 v4.2 的体验原则

1. **缓存先于调用**：已有可信数据时不为了“看起来实时”重复请求外部 API。
2. **观点先于材料**：报告先说明有哪些可成立的观点，再说明每个观点由什么支持。
3. **对话可见且可恢复**：用户与 AI 的每一条消息都应即时可见、持久化且可区分归属。
4. **反馈必须真实**：刘看山只反映真实的请求和会话状态，不由点击触发，也不制造持续“思考中”假象。
5. **陪练先于诘问**：AI 可以直接回答用户的问题；追问用于推动思考，而非逼迫用户提交事实、数据或案例。

## 一、v4.2 主链路

```text
首页
  ├─ 输入问题
  └─ 知乎热榜 Top 10
       └─ 6 小时内持久化缓存 → 不调用 API
          过期缓存 → 尝试刷新 → 旧缓存 → mock
             ↓
多源检索与报告
  └─ 多个核心观点
       └─ 每个观点的关键依据
            └─ 综合结论（支撑度、适用条件、现实可行性）
                 ↓
选择或输入初始观点
                 ↓
温和对话式思辨
  ├─ 用户提问：AI 先回答，再给一个温和追问
  ├─ 用户作答：AI 承接观点，再按策略引导
  ├─ 三轮定向提问后：继续聊 / 生成总结
  └─ 任意时刻：生成总结
                 ↓
成果卡与会话保存
```

## 二、热榜：6 小时持久化缓存与可信降级

### 2.1 目标

首页热榜应优先展示本地数据库中的最近可信快照。用户再次启动应用时，只要缓存仍在有效期内，就直接使用缓存，不调用知乎 API。

### 2.2 缓存契约

热榜是全局公开数据，不按用户或匿名 owner 分片。服务端维护一份最新成功快照，包含：

- `items`：规范化后的 Top 10 条目；
- `updatedAt`：该快照实际成功获取的时间；
- `source`：`live`、`cache` 或 `demo`；
- `stale`：仅在使用过期缓存时为 `true`。

TTL 固定为 **6 小时**。`/api/hotlist` 的决策顺序如下：

| 条件 | 行为 | 返回标识 |
|---|---|---|
| 存在未过期数据库快照 | 直接返回；不得调用外部 API | `cache` |
| 快照已过期，实时拉取成功 | 覆盖保存快照并返回 | `live` |
| 快照已过期，实时拉取失败 | 返回旧快照，保留真实更新时间 | `cache` + `stale: true` |
| 无任何快照且实时拉取失败 | 返回确定性 mock | `demo` |
| 数据库不可用 | 记录原始错误；不伪造缓存 | 视实时结果返回 `live` 或 `demo` |

mock 数据不得写入为“成功的真实热榜缓存”，也不得标记为实时数据。外部 API、认证、超时、HTTP 451、额度或数据库失败均应有一次可追踪的降级结论，不无限重试。

### 2.3 首页表达

热榜区必须显示真实来源与时间：

- `实时热榜`；
- `缓存 · 更新于 YYYY-MM-DD HH:mm`；
- `缓存已过期 · 更新于 YYYY-MM-DD HH:mm`；
- `演示数据`。

热榜失败不能被静默吞掉：使用 mock 时需以低干扰方式说明当前为演示数据；使用旧缓存时需说明其过期状态。

### 2.4 验收

- 有效缓存下 transport/API 调用次数为零；
- 过期缓存刷新成功后写入新快照；
- 过期缓存刷新失败时仍显示旧数据且标记过期；
- 没有缓存时才使用 mock；
- 数据库故障不伪造 `cache` 或 `live`；
- 浏览器级测试验证四种来源状态及首页展示。

## 三、报告：多个观点与按观点组织的依据

### 3.1 报告阅读目标

报告不是材料堆叠或长摘要。用户应在短时间内回答：

1. 围绕这个问题，当前有哪些明确、可区分的观点？
2. 每个观点最关键的依据是什么？
3. 综合现有材料，哪些观点支撑更多、在哪些条件下更可行？

开放式问题允许存在多个合理观点；产品不得强行选择唯一正确答案。

### 3.2 结构化输出契约

报告生成器和渲染层使用结构化字段，不由 UI 从长 Markdown 中猜测层级。

```ts
type ReportEvidence = {
  summary: string;
  citationIds: number[];
};

type ReportViewpoint = {
  id: string;
  conclusion: string;
  evidence: ReportEvidence[];
};

type StructuredReport = {
  title: string;
  viewpoints: ReportViewpoint[];
  synthesis: string;
};
```

字段约束：

- `conclusion` 必须是明确的观点或判断，不能只是案例、来源标题或泛泛背景；
- `evidence` 只放与其所属观点直接相关的短依据；长案例、原文摘抄不能替代观点；
- `citationIds` 只能指向真实存在的报告引用；没有直接来源的 AI 综合必须诚实标记，不得伪造；
- `synthesis` 用于比较不同观点的支撑度、适用条件和现实可行性，不宣布唯一答案；
- 不设独立的“问题关联”或“反例/限制”区块。

### 3.3 页面布局

```text
报告标题
  ↓
核心观点
  ├─ 观点 A：明确结论
  │    ├─ 关键依据 1 [引用]
  │    └─ 关键依据 2 [引用]
  ├─ 观点 B：明确结论
  │    └─ 关键依据 1 [引用]
  ↓
综合结论
  └─ 各观点的支撑度、适用条件与现实可行性
  ↓
知识图谱、观点引导、分类引用
```

旧会话或旧报告缺少结构化字段时，界面应安全降级并明确其为旧格式；不得伪造新的观点或依据。

### 3.4 验收

- 同一报告可显示多个观点；
- 每条依据只归属到一个明确观点，引用可追溯；
- 长案例不出现在核心观点或综合结论中替代判断；
- 综合结论比较观点，不武断裁决；
- 旧报告能安全显示；
- 单元、集成和浏览器 Golden Path 覆盖结构、引用和段落可读性。

## 四、会话：完整历史、即时回显与真实状态

### 4.1 消息归属与持久化

会话历史是用户和 AI 共同形成的交互记录，但两者归属必须始终明确：

| 消息类别 | 归属 | 是否可进入成果卡/画像 |
|---|---|---|
| 用户提问、回答、观点 | 用户 | 仅在规则允许时可用 |
| AI 直接回答 | AI | 不得写成用户观点 |
| AI 温和追问 | AI | 不得写成用户观点 |
| 系统状态或失败提示 | 系统 | 不进入成果卡或画像 |

所有 AI 的回答和追问均须作为 assistant message 持久化。刷新或恢复会话后，用户必须能看到完整历史，而不是只看到当前待回答的问题。

### 4.2 即时发送体验

用户点击发送后：

1. 客户端立即在对话区插入用户消息，并显示 `pending`；
2. 请求在后台发送；
3. 服务端成功返回后，以持久化消息确认并对齐；
4. 失败时保留原消息，标明失败并提供一次明确的重试路径；
5. 不得静默丢失、重复保存或重复发送用户内容。

### 4.3 刘看山状态

刘看山是状态提示，不是可点击的播放开关。状态由真实请求和会话状态派生：

| 实际状态 | 反馈 |
|---|---|
| 报告/热榜请求进行中 | `retrieving` |
| AI 正在组织回答或追问 | 与当前策略对应的 `questioning` 或 `challenging` |
| 等待用户输入 | 静态、可见的文字提示；不伪称“正在思考” |
| 会话完成 | `completed` |

GIF 在非 reduced-motion 环境中自动播放；点击不得启动、锁死或改变业务状态。reduced-motion 或资源加载失败时，文字必须完整可见。

### 4.4 验收

- 用户消息发送瞬间可见；
- AI 历史消息刷新后仍可见；
- 失败不丢失用户输入；
- AI 请求时刘看山自动反馈，等待输入时不持续假动画；
- 不依赖点击控制动效；
- reduced-motion 与资源失败均保持文本等价；
- E2E 覆盖发送、回复、刷新恢复和失败路径。

## 五、温和自适应思辨

### 5.1 定位

v4.2 保留 v4.1 的策略类别作为内部覆盖检查，但把交互从固定、强对抗的轮次推进改为“老师式”的对话引导：先理解用户正在做什么，再选择回应或追问。

### 5.2 输入意图

系统至少区分两类用户输入：

| 用户意图 | AI 行为 | 是否推进定向轮次 |
|---|---|---|
| 用户在提问 | 先直接、简短、诚实回答；再给一个最多一句的温和追问 | 否 |
| 用户在回答或表达观点 | 先承接其核心判断；再按当前策略给一个温和问题 | 是，前提是实质性表达 |

分类可采用确定性规则与受控 LLM 辅助；失败时默认按“用户回答”处理，但语气必须温和。分类结果、回复和追问都不得伪造用户立场或外部事实。

### 5.3 三轮定向关口

1. 用户完成三轮实质性的、策略定向的回答后，显示 `继续聊 / 生成总结`；
2. 用户可随时主动生成总结；
3. 用户选择继续后保持对话式节奏，后续每三轮再次提供相同选择；
4. 用户提问、澄清和非实质性短回应不应被错误计入三轮；
5. 不再要求默认完成固定五轮，也不因用户未提供数据、案例而施压。

### 5.4 语气与护栏

- 像耐心老师：承接、澄清、邀请思考；
- 每次最多一个追问；
- 不羞辱、审判、逼迫反驳或要求事实举证；
- 只有上下文确实需要时，才温和邀请用户补充依据；
- AI 可以回答问题，但不能替用户形成或归属用户结论；
- LLM 失败、超时、451、认证或额度失败时，记录原始错误，停止重复尝试，使用诚实的温和模板降级。

### 5.5 成果卡

成果卡仍严格基于用户消息。AI 的直接回答、追问、总结建议和任何未被用户明确采用的观点都不得当作用户表达。三轮关口只影响何时建议总结，不等同于对用户“完成思考”的评价。

### 5.6 验收

- 用户提问先得到直接回答，再得到温和追问；
- 用户的实质回答才推进定向轮次；
- 三轮后出现继续/总结，且可以随时总结；
- AI 回复和追问可在历史中恢复；
- LLM 失败后流程可继续、降级状态诚实；
- 单元、集成和浏览器 Golden Path 分别覆盖“用户提问”与“用户作答”。

## 六、实现边界与数据诚实性

### 6.1 明确不做

- 不在本版本实现新模式入口、完整八策略、知识库、相关推荐、语音、数字人、分享或账户；
- 不把缓存、mock、AI 综合或历史报告伪装为实时外部事实；
- 不使用 `as any`、删除测试或弱化断言掩盖契约问题；
- 不在浏览器调用服务端数据库能力，也不在服务端导入 clientStorage；
- 不预先实现后续票的模式能力。

### 6.2 质量与交付要求

每张实现票均需独立 worktree、Builder/Reviewer/Finalizer 门禁、可复现 handoff 和以下质量门禁：

```text
npm run typecheck
npm run lint
npm test
npm run build
npm run test:e2e
```

所有门禁全绿、P0/P1 清零、diff scope 合格、工作树干净，才具备合并条件。真实 Zhihu、LLM、Neon 或 Vercel 环境未受控验收时，只能表述为“代码与 fake/integration 测试通过，真实接入待受控环境验收”。

## 八、版本变更摘要

v4.2 相对 v4.1：

- 将热榜从“24 小时、实时优先”改为“6 小时、数据库缓存优先”；
- 将报告从“核心知识点 + 长正文 + 观点速览”调整为“多个核心观点 + 各自关键依据 + 综合结论”；
- 明确完整 AI/用户消息历史、即时用户回显和刷新恢复；
- 将刘看山定义为真实派生的会话反馈，而非点击控制的动效；
- 将 MVP 标准诘问从固定前五轮改为温和、自适应的三轮定向关口；
- 保留用户可随时结束、成果卡严格基于用户表达、来源与降级诚实等 v4.1 基本原则；
- 补充 #50 官方原始素材必须被版本控制并可在 fresh clone 复现的要求。
