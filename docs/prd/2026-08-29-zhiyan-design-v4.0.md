## 一、产品顶层设计

### 1.1 核心定位

> **知研——AI 时代的思辨陪练平台。**

AI 时代的大多数产品遵循“人问 AI、AI 给答案”，知研反转这一关系：

> **AI 问人。**

知研不替用户形成观点，而是通过资料报告、观点引导和连续诘问，帮助用户发现论证中的证据缺口、隐藏前提和反方挑战，最终形成更扎实、更独特的见解。

### 1.2 价值主张

| 传统 AI 模式 | 知研模式 |
|---|---|
| 人问 AI，快速得到答案 | AI 问人，引导用户形成答案 |
| AI 替代部分思考 | AI 促进主动思考 |
| 输出一份看似完整的结论 | 保留用户观点的形成过程 |
| 用户消费内容 | 用户生产和打磨观点 |

一句话定位：

> **让 AI 帮助人类发掘独特见解，而非替代人类思考。**

### 1.3 知乎生态价值

知研将知乎内容从“阅读材料”转化为“思辨弹药”：

- 知乎创作者可在发布回答前检查论证、补足证据并预演反方质疑。
- 知乎读者可从热榜或问题出发，不止浏览观点，还能形成自己的判断。
- 高质量知乎回答、精选评论和互动信号成为报告及诘问的可追溯来源。
- 经打磨后的观点可反哺知乎内容质量，形成“阅读—思考—表达”的闭环。

### 1.4 目标用户

| 用户类型 | 典型需求 | 典型场景 |
|---|---|---|
| 知乎创作者 | 发布前打磨观点 | 回答、文章、争议话题创作 |
| 已有观点的普通用户 | 让自己的想法更完整 | 日常判断、公共议题、个人选择 |
| AI 从业者 | 验证技术或产品假设 | 技术路线、产品决策 |
| 科研者 | 审视论证严谨性 | 研究观点、答辩准备 |
| 企业管理者 | 检查决策前提与风险 | 战略讨论、方案评审 |
| 场景准备者 | 预演高压提问 | 面试、演讲、答辩 |

黑客松 MVP 优先覆盖前两类用户：知乎创作者，以及已经形成初步观点、希望进一步打磨的用户。

### 1.5 设计原则

1. **陪练而非裁判**：指出论证缺口，但不替用户裁决争议立场。
2. **忠于用户表达**：不能把 AI 的观点、问题或补充误写成用户观点。
3. **来源可追溯**：外部事实、报告引用和知识图谱关系均需标记来源或推断属性。
4. **渐进增强**：先完成一种可靠的标准模式，再通过配置和接口扩展其他模式。
5. **失败可降级**：外部 API 或 LLM 不稳定时，核心流程仍可完成。

### 2.2 两种进入方式

#### 自定义问题

用户输入希望思考的问题。问题输入框下提供默认折叠的“补充我的初步看法（可选）”。初始观点进入诘问上下文，但不用于过滤搜索结果，避免只检索支持用户立场的内容。

#### 知乎热榜

首页通过知乎热榜 API 获取并展示 Top 10。点击话题后进入确认步骤：用户可以直接生成报告，也可以先补充初始观点。

### 2.3 报告是必经步骤

MVP 不提供绕过报告直接诘问的入口。报告为后续诘问提供事实背景、争议视角和可引用材料；已有观点的用户仍先获得报告，再进入观点打磨。

## 三、报告与多源检索

### 3.1 数据来源

报告生成并行使用三类来源：

| 来源 | 定位 | 权重原则 |
|---|---|---|
| 知乎站内搜索 | 报告主干，体现社区讨论与知乎生态价值 | 相关度优先，结合权威度、互动信号和观点多样性 |
| 全网搜索 | 补充外部事实、不同视角和权威材料 | 相关度与来源可靠性优先 |
| 我的历史报告 RAG | 提供跨会话背景和个性化上下文 | 不因符合用户旧观点而提高事实权重 |

检索结果先去重，再按相关度、权威度和观点多样性重排。历史报告只能作为个性化背景，不能被包装成外部事实来源。

### 3.2 历史报告引用

系统自动检索相关历史报告，并将实际使用的报告放入报告底部引用列表。每条历史报告引用显示标题与生成时间。MVP 不提供精细的历史报告选择器；用户可在引用区移除不希望使用的历史报告并重新生成。

### 3.3 报告结构

报告自上而下包含：

1. 报告标题
2. 核心知识点摘要
3. 话题概述与主要内容
4. 主要观点与争议
5. 知识图谱
6. 三个观点引导选项
7. 引用列表
8. 相关推荐（后续功能）

报告页面的纵向信息结构如下：

```text
┌──────────────────────────────────────────────────────────────┐
│ 顶部：报告标题                                                │
├──────────────────────────────────────────────────────────────┤
│ 📌 核心知识点                                                 │
│ • 最重要的结论与背景                                          │
│ • 用户进入思辨前必须知道的信息                                │
├──────────────────────────────────────────────────────────────┤
│ 中部：📖 话题概述与主要内容                                   │
│ • 知乎社区中的主要讨论                                        │
│ • 全网资料补充                                                 │
├──────────────────────────────────────────────────────────────┤
│ ⚡ 主要观点与争议                                             │
│ • 支持视角  • 反对视角  • 关键分歧                           │
├──────────────────────────────────────────────────────────────┤
│ 🕸️ 知识图谱                                                  │
│ • 核心实体  • 实体关系  • 来源/推断状态                       │
├──────────────────────────────────────────────────────────────┤
│ ✨ 三个观点引导选项                                           │
│ [选择观点 A] [选择观点 B] [选择观点 C]                        │
│ 或者：直接输入自己的观点                                      │
├──────────────────────────────────────────────────────────────┤
│ 底部：📚 分类引用列表                                         │
│ [知乎来源] [全网来源] [我的历史报告] [AI 综合分析]            │
├──────────────────────────────────────────────────────────────┤
│ 🔗 相关推荐（未来功能）                                       │
└──────────────────────────────────────────────────────────────┘
```

### 3.4 引用与溯源

正文中的关键事实和归纳使用 `[1]`、`[2]` 等编号。报告底部按以下类型分组：

- 知乎来源
- 全网来源
- 我的历史报告
- AI 综合分析（没有单一直接来源的归纳，不得伪装成事实引用）

引用只使用真实检索结果。不得补造作者、链接、标题、原文或互动数据。搜索摘要不是完整原文，界面需避免将其展示成逐字引文。

### 3.5 知识图谱

知识图谱在报告生成时同步构建，用于展示核心概念及其关系。

MVP 规格：

- 每份报告展示 6～10 个核心实体。
- 关系使用少量清晰动词描述。
- 支持缩放、拖动和点击节点。
- 点击节点展示关联摘要及引用来源。
- 不提供自由编辑、复杂筛选和跨报告大图谱。

每条关系必须具有来源类型：

| 类型 | 含义 |
|---|---|
| `supported` | 有检索来源直接或明确支持，关联引用编号 |
| `inferred` | AI 根据多段材料归纳，界面明确标记“推断” |
| `user_claimed` | 来源于用户自己的表达，关联用户消息 |

模型推断不能以确定事实的视觉样式呈现。

知识图谱示意：

```text
                         ┌────────────┐
                         │  核心议题  │
                         └─────┬──────┘
                  supported   │   inferred
                  [引用 1]     │   [AI 推断]
             ┌────────────────┴──────────────┐
             ▼                               ▼
       ┌────────────┐                  ┌────────────┐
       │ 支持性证据 │                  │ 潜在影响   │
       └─────┬──────┘                  └─────┬──────┘
             │ user_claimed                  │ supported
             │ [用户消息 3]                  │ [引用 4]
             ▼                               ▼
       ┌────────────┐                  ┌────────────┐
       │ 用户主张   │◄────── 对立 ────►│ 反方观点   │
       └────────────┘                  └────────────┘

点击节点 → 关系说明 → 来源编号 → 查看报告引用或原始消息
```

### 3.6 生成进度

报告生成过程展示真实阶段：

1. 正在检索知乎内容
2. 正在检索全网资料
3. 正在查找历史报告
4. 正在整理观点与争议
5. 正在构建知识图谱

报告正文允许渐进展示，知识图谱可以最后异步补充。观点引导完成前，右侧诘问输入暂不可用。

## 四、观点引导模块

### 4.1 触发位置

报告生成完成后、诘问开始前，系统基于报告和简化用户画像生成三个不同切入角度。用户也可以直接输入自己的观点。

### 4.2 选项原则

- 三个选项应有实质差异，不只是同一句话的改写。
- 至少覆盖不同立场、前提或实践角度。
- 选项必须基于报告，不凭空增加事实。
- 选项只降低表达门槛，不暗示存在唯一正确立场。

### 4.3 内容归属

所有观点内容保存来源：

| 来源 | 说明 |
|---|---|
| `user_authored` | 用户亲自输入 |
| `ai_suggested_user_selected` | AI 生成、用户明确选择 |
| `ai_authored` | AI 生成但用户未选择 |

成果卡可以使用前两类，但必须分别表述为“用户表达”与“用户选择的初始立场”。未被选择的 AI 内容不能进入用户画像。

## 五、诘问模式完整蓝图

### 5.1 正常诘问

- 定位：默认、通用的观点打磨模式。
- 时间：不限定总时长。
- 强度：标准。
- 策略：完整产品支持 8 种策略；MVP 只启用 4 种核心策略。

### 5.2 快速诘问

- 定位：在 5～30 分钟内完成特定功利目标。
- 场景：面试、答辩、演讲和重要沟通准备。
- 能力：目标设定、时限、强度调节、即时反馈和场景化提问。
- 状态：MVP 预留接口，后续实现。

### 5.3 深度诘问

- 定位：无时间压力地追求认知升级。
- 强度：最高，从犀利起步并逐步升级。
- 能力：8 种策略、高级组合、策略联动、立场变化与认知轨迹追踪。
- 状态：MVP 预留接口，后续实现。

### 5.4 趣味诘问

- 定位：在正常或深度诘问引擎上叠加活泼表达风格。
- 风格：古风、二次元、轻松及未来自定义风格。
- 交互：保持对话式，不使用独立游戏弹窗。
- 状态：MVP 预留接口，后续实现。

### 5.5 GalGame 模式

- 定位：独立的沉浸式思辨游戏。
- 内容：LLM 生成情景剧本、角色对话和剧情选项。
- 表现：刘看山表情或动画作为情景背景。
- 交互：独立弹窗或游戏窗口，不与趣味诘问混同。
- 未来入口：报告生成后的会话页右侧，位于刘看山 GIF 旁。
- 状态：不属于 MVP；未实现前不展示不可用入口。

未来交互示意：

```text

│ 🎮 GalGame 思辨剧场                              [关闭]       │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│              ┌────────────────────────────┐                  │
│              │ 刘看山情景表情 / 动态背景 │                  │
│              └────────────────────────────┘                  │
│                                                              │
│ 剧情：根据当前问题和用户画像生成的思辨情境                    │
│                                                              │
│ 刘看山：「如果你的关键前提并不成立，你会怎么选择？」          │
│                                                              │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ 选项 A：坚持原立场并补充证据                              │ │
```

## 六、诘问引擎

### 6.1 完整策略库

| 编号 | 名称 | 追问方向 | 难度 | MVP |
|---|---|---|---|---|
| M1 | 证据追问 | 判断依据、数据或具体例子 | L1 | 是 |
| M2 | 前提追问 | 揭示未明说的前提假设 | L2 | 是 |
| M3 | 锚定揭露 | 检查是否受首个或高赞观点锚定 | L2 | 否 |
| M4 | 钢铁人反驳 | 面对对方最强论点 | L3 | 是 |
| M5 | 系统二激活 | 区分直觉反应与审慎推理 | L2 | 否 |
| M6 | 立场反转 | 从对立立场重新论证 | L3 | 是 |
| M7 | 元认知 | 观察观点形成过程 | L4 | 否 |
| M8 | 立场崩塌检测 | 检查内部矛盾与不可兼容主张 | L4 | 否 |

### 6.2 调度机制

策略选择与问句生成分离：

1. 程序根据会话状态、历史策略和用户回答筛选候选策略。
2. 程序限制连续重复，必要时降低或提高难度。
3. LLM 只能在候选策略范围内生成下一问。
4. 输出经过问句、攻击性语言和越权结论检查。

未来模式通过配置改变可用策略、强度、轮次和提示词，不复制一套新的诘问引擎。

```text
┌────────────────────────────────────────────────────────────────────┐
│                           用户本轮回答                              │
└──────────────────────────────┬─────────────────────────────────────┘
                               ▼
┌────────────────────────────────────────────────────────────────────┐
│                            上下文层                                 │
│ 报告弹药 + 引用 + 会话历史 + 简化画像 + 当前 ModeConfig           │
└──────────────────────────────┬─────────────────────────────────────┘
                               ▼
┌────────────────────────────────────────────────────────────────────┐
│                         策略候选调度器                              │
│ 适用性判断 → 防重复 → 难度调整 → 候选 M1/M2/M4/M6                 │
└──────────────────────────────┬─────────────────────────────────────┘
                               ▼
┌────────────────────────────────────────────────────────────────────┐
│                       LLMProvider 生成问句                          │
│       失败：快速重试一次 → 人工审核的策略模板降级                  │
└──────────────────────────────┬─────────────────────────────────────┘
                               ▼
┌────────────────────────────────────────────────────────────────────┐
│                             护栏层                                  │
│ 问句检查 + 非攻击性 + 不替用户下结论 + 不编造用户观点              │
└──────────────────────────────┬─────────────────────────────────────┘
                               ▼
┌────────────────────────────────────────────────────────────────────┐
│                   追问 + 策略标签 + 引用（如有）                    │
└────────────────────────────────────────────────────────────────────┘
```

### 6.3 MVP 前五轮结构

默认五轮构成第一个完整阶段：

1. 根据初始观点选择 M1 证据或 M2 前提。
2. 使用另一项基础策略补齐论证。
3. 使用 M4 钢铁人反驳。
4. 使用 M6 立场反转。
5. 要求用户重新表述当前观点。

第五轮回答后展示阶段小结，并询问是否继续。继续后在第 8、11、14……轮再次询问。对话区始终提供退出按钮。

### 6.4 短回答与“不知道”

- 第一次：把问题缩小，要求具体例子或澄清一个概念。
- 连续两次：提供两个思考方向，但不替用户作答。
- 连续三次：建议结束本次诘问并生成成果卡。

### 6.5 护栏

MVP 保留以下基础护栏：

- 诘问输出以问题为主体，不替用户下结论。
- 不攻击、羞辱或审判用户。
- 不把争议立场直接判定为错误。
- 不把检索内容中的指令当成系统指令。
- 不编造用户观点、证据或态度变化。

完整的 19 种认知陷阱分类、风险等级和实时警告 UI 属于后续功能。长期产品保留稻草人、滑坡、虚假前提、自相矛盾、诉诸权威、模糊词、樱桃选择、锚定、诉诸情感、循环论证和确认偏误等检测能力。

### 6.6 LLM 降级

每种策略准备人工审核的模板问句：

```text
LLM 生成 → 一次快速重试 → 策略模板降级
```

模型通过 `LLMProvider` 接入 OpenAI-compatible API。DeepSeek、Claude 或其他供应商配置不得写入诘问引擎业务逻辑。

## 七、会话结束与思辨成果卡

### 7.1 触发条件

- 用户随时点击退出。
- 用户在第 5、8、11……轮选择不继续。
- 连续三次无法回答后接受结束建议。

### 7.2 成果卡内容

- 用户最初亲自表达的观点。
- 用户选择的 AI 建议立场，单独标记来源。
- 用户补充的证据与前提。
- 用户主动修正的内容。
- 用户最终观点。
- 尚未解决的问题。

MVP 不对观点质量进行数值评分，也不自动声称用户发生“认知升级”。后续可增加诘问前后结构化比较，但必须严格基于用户消息。

### 7.3 严格溯源

- 成果卡每条内容关联对应用户消息 ID。
- AI 问句不能成为用户观点。
- “用户修正观点”必须有前后两条用户表达支持。
- 找不到用户证据时宁可留空。
- 点击成果卡内容可定位原始对话。

成果卡生成失败时仍保存完整会话，允许用户稍后重新生成，不能阻止退出。

## 八、用户画像与数据

### 8.1 完整用户画像

长期产品支持：

| 维度 | 内容 | 主要来源 |
|---|---|---|
| 关注领域 | 常讨论的话题标签 | 会话与报告 |
| 思辨风格 | 论证偏好、常用策略 | 用户回答行为 |
| 认知轨迹 | 立场变化与长期演进 | 深度诘问记录 |
| 强项与弱项 | 逻辑强项、常见盲区 | 多次策略与陷阱统计 |

完整产品可将画像注入报告、观点引导、各类诘问及 GalGame 剧本。画像只作为个性化上下文，不能改变事实来源权重。

### 8.2 MVP 简化画像

MVP 只提取关注领域与思辨风格。会话结束、成果卡生成后统一更新，不在每轮实时改写。

每个画像结论保存：字段、置信度、来源会话、对应用户消息 ID 和更新时间。AI 未被选择的建议不能进入画像；用户选择的 AI 建议只作为低权重证据。

### 8.3 可见性与删除

MVP 不建设完整画像管理页，但提供清除画像入口。用户删除画像后：

- 会话和报告继续保留。
- 系统不得从旧会话静默重建画像。
- 只从删除后的新会话重新积累画像。
- 用户主动发起报告 RAG 时仍可检索保留的历史报告。

后续版本允许用户查看、修正和管理画像字段。

### 8.4 保存规则

| 数据 | 保存规则 |
|---|---|
| 知乎站内及全网搜索缓存 | 滚动 24 小时 |
| 知乎热榜 Top 10 | 每日首次访问更新，缓存 24 小时；失败沿用上一版 |
| 用户报告 | 长期保存，直到用户删除 |
| 会话记录 | 长期保存，直到用户删除 |
| 用户画像 | 长期保存，支持单独删除 |

报告不设置 TTL。搜索缓存与用户资产使用不同生命周期。

### 8.5 会话恢复

- 未结束的会话可以继续。
- 已生成成果卡的会话保持只读。
- 用户可以基于已结束会话开启新一轮，形成新的会话与成果卡。

## 十、黑客松 MVP 范围

### 10.1 MVP 目标

用一条完整、流畅、可降级的链路证明：知乎内容可以成为用户思考的弹药，AI 可以通过追问帮助用户打磨自己的观点。

MVP 优先服务完成度与核心体验，不同时实现所有长期模式。

### 10.2 必须实现

| 模块 | MVP 要求 | 优先级 |
|---|---|---|
| 首页 | 问题输入、可选初始观点、知乎热榜 Top 10 | P0 |
| 热榜 | 每日更新、24 小时缓存、失败沿用旧缓存 | P0 |
| 多源检索 | 知乎站内搜索、全网搜索、历史报告 RAG | P0 |
| 报告 | 摘要、主要内容、观点与争议 | P0 |
| 引用 | 正文编号，底部按三类来源展示 | P0 |
| 知识图谱 | 6～10 个实体、关系类型、来源状态、基础交互 | P0 |
| 观点引导 | 三个差异化选项与自定义观点 | P0 |
| 标准诘问 | 单一标准模式、程序调度与 LLM 生成 | P0 |
| 核心策略 | M1、M2、M4、M6 | P0 |
| 轮次控制 | 第 5 轮询问，随后每 3 轮询问，随时退出 | P0 |
| 降级 | 短回答引导、LLM 模板、搜索缓存和演示数据 | P0 |
| 成果卡 | 严格基于用户消息整理观点变化 | P0 |
| 数据保存 | 报告、会话与简化画像长期保存 | P0 |
| 刘看山 | 少量阶段状态 GIF | P0 |

### 10.3 预留接口但暂不实现

- 快速、深度、趣味和 GalGame 模式。
- 完整 8 种策略与 19 种陷阱检测。
- 哲学、辩论、逻辑和垂直领域内置知识库。
- 刘看山高级自定义设置。
- 相关推荐、会话分享、语音和数字人。
- 正式知乎 OAuth 登录。

### 10.4 明确不进入 MVP

- 完整注册、邮箱验证和密码找回系统。
- GalGame 剧本、成就和动态剧情。
- 对观点质量进行自动评分。
- 自动宣称用户实现认知升级。
- 跨报告知识图谱与图谱编辑器。
- 画像完整可视化管理后台。

### 10.5 MVP 验收链路

```text
首页加载知乎热榜 Top 10
  → 选择热榜或输入问题
  → 可选填写初始观点
  → 展示多源检索进度
  → 生成带引用的报告与知识图谱
  → 选择观点或自行输入
  → 完成标准诘问前五轮
  → 选择结束或继续
  → 生成可溯源成果卡
  → 保存会话并更新简化画像
```

### 10.6 性能与降级目标

- 2 秒内出现可见进度反馈。
- 尽量在 15 秒内完成报告正文。
- 20 秒仍未完成则切换缓存降级。
- 知识图谱允许在正文后异步完成。
- LLM 问句失败后重试一次，再使用人工模板。

外部数据降级顺序：

1. 实时知乎与全网搜索。
2. 相同查询的 24 小时缓存或最近一次可用缓存。
3. 本地预置演示数据。

界面使用低干扰状态标识：`实时检索`、`缓存 · 更新时间`、`演示数据`，不得把缓存静默伪装成实时结果。

### 11.3 身份与 OAuth

MVP 默认使用匿名设备身份关联会话、报告和简化画像，并准备固定演示账号作为降级。

正式比赛接入时可实现 `ZhihuOAuthProvider`。知乎官方 `zhihu-cli` Skill 提供 OAuth 接口资料，但 CLI 日常认证本身不执行 OAuth。真实知乎登录要求：

- 申请 `app_id` 与 `app_key`。
- 使用公网 HTTPS 回调地址，本地地址只能预览。
- 后端安全保存 `app_key` 与 OAuth token。
- 同时正确使用开放平台 Access Secret 与用户 OAuth token。

当前 OAuth 资料缺少可靠的 state、PKCE、刷新和撤销协议，因此只作为黑客松联调能力，不能直接宣称为生产级认证。

### 11.4 各模式默认 LLM 参数

以下参数属于长期产品的默认配置，由 `ModeConfig` 交给具体 `LLMProvider`。供应商不支持某个参数时，由适配层忽略或转换，业务引擎不直接判断模型品牌。

| 模式 | temperature | top_p | top_k | 设计目的 |
|---|---:|---:|---:|---|
| 正常诘问 | 0.7 | 0.9 | 50 | 在稳定性与开放性之间平衡 |
| 快速诘问 | 0.6 | 0.85 | 40 | 更确定、更目标导向 |
| 深度诘问 | 0.8 | 0.95 | 60 | 提高探索性与问题深度 |
| 趣味诘问 | 0.85 | 0.95 | 50 | 提高语言风格的活泼程度 |
| GalGame | 1.0 | 1.0 | 不指定 | 提高剧情和选项的多样性 |

用户未来可通过刘看山设置调整参数，但所有配置都必须经过供应商能力校验、范围限制和安全护栏。

## 十四、成功标准

### 14.1 AI 场景价值

- 用户能明显理解“AI 问人”与普通问答机器人的差异。
- 知乎内容确实参与报告和诘问，而非只作为装饰入口。
- 成果卡能够展示用户观点被补充、澄清或修正的过程。

### 14.2 创新度

- 用连续诘问替代直接给答案。
- 将报告、真实社区观点、知识图谱和思辨过程连接为一条体验。
- 刘看山承担陪练角色，但不让游戏化掩盖核心价值。

### 14.3 完成度

- Golden Path 可完整跑通。
- 外部 API 与 LLM 失败均有可见、诚实的降级路径。
- 不展示尚不可用的模式入口。

### 14.4 产品体验与设计感

- 报告与对话左右分工清楚。
- 等待过程有真实进度反馈。
- 引用、图谱关系和成果卡均可追溯。
- 用户始终可以退出，不被强迫完成固定轮数。
