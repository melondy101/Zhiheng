# 快速诘问与报告定向阶段设计

日期：2026-09-01  
状态：已达成设计共识，待用户审阅；未授权实现

## 目标与范围

MVP 完成后，先交付快速诘问。它解决“用户刚读完报告、尚未形成可被挑战的判断”时直接进入诘问容易空泛的问题。

快速、深度与趣味模式复用同一诘问引擎。趣味模式只叠加表达与呈现风格；GalGame 保持独立产品形态，不在本设计内。账号、Cookie 会话与游客数据认领也不在本设计范围，须等 Demo 预定功能全部完成后再启动。

## 体验流程

```text
报告与观点选择
  → orientation（报告理解与观点澄清，最多两轮）
  → transitionChoice（必须显示轻量选择卡）
  → 用户选择固定动作
  → interrogation（正式策略调度与回合计数）
  → 检查点 / 完成
```

定向阶段帮助用户选择关注点、复述理解或表达暂时倾向。AI 判断准备度只用于生成建议，不可自行切换到正式诘问。两轮后必须出现选择卡；用户可选择继续定向，但该选择必须是显式的。

## 固定动作与 AI 边界

选择卡只允许以下动作类型：

- `challenge_claim`：开始挑战当前判断。
- `inspect_evidence`：先检查判断依据。
- `inspect_counterargument`：先理解最强反方。
- `continue_orientation`：继续梳理报告。

LLM 只能针对当前报告、已保存的用户回答和可用来源，为固定动作填充具体文案、生成中性摘要并推荐一个动作。服务端验证动作类型、数量、来源和安全文案后才持久化。LLM 失败时使用人工审核的固定选择文案，选择卡始终可用。

AI 不得创建新的动作、替用户确认立场、自动改变会话阶段，或把报告内容伪装成用户表达。

## 数据与状态机

`Session` 扩展为持久化以下信息：

- `mode`：`quick`、未来的 `deep`，以及可叠加的表现风格。
- `phase`：`orientation`、`transitionChoice` 或 `interrogation`。
- 定向轮次数。
- 选择卡的动作类型、具体文案、推荐项及关联的报告来源。

定向回答以普通用户消息保存，标记 `phase: orientation`。它们可以成为成果卡的可追溯证据，但不计入正式诘问轮数、策略历史、五轮检查点或不确定回答的正式回合计算。刷新恢复必须展示原有选择卡，不能重新生成或改变推荐。

正式诘问仍由服务端状态机推进；用户点击选择卡后才进入 `interrogation` 并调用策略调度器。

## ModeConfig

所有模式由同一 `ModeConfig` 描述，而不是复制状态机：

- `orientationMaxRounds`
- `allowedStrategies`
- `checkpointPolicy`
- `intensityPolicy`
- `presentationStyle`

快速模式：最多两轮定向、3–5 轮目标导向正式诘问。深度模式后续在相同契约上扩展到八策略、强度递进与认知轨迹。趣味模式继承快速或深度的业务配置，仅替换表达和视觉呈现。

### 趣味模式与内置角色

趣味模式是上述模式的表现层，而非独立诘问状态机。首次交付时，用户点击趣味模式后选择一个内置角色，并以**快速模式**作为默认且唯一的底层节奏；深度模式完成后，是否开放其作为趣味模式的底层节奏须另行设计。

首批内置角色：

- `轻松朋友`：鼓励、口语化、低压力追问。
- `古风辩友`：克制、典雅，以反问和类比推进。
- `二次元搭档`：活泼，但不幼化或回避严肃问题。

角色配置是受控数据，包含名称、简介、语气约束、禁用表达与视觉资源引用；LLM 只能按配置改写表达。视觉资源接口允许未来为不同角色配置不同资源，但首版所有角色都使用同一套刘看山资源，角色差异仅来自语言与状态文案。角色不得改变策略、证据来源、选择卡动作、轮次、检查点、退出、成果卡归因或“不替用户裁决”护栏。角色在会话创建时持久化并锁定，**不允许中途切换**；要更换角色，用户从当前报告新开会话。

## 验收与失败路径

- 定向阶段在两轮后显示选择卡；用户未选择不得开始正式诘问。
- 每种固定动作均可进入正确后续路径，且 AI 推荐不能覆盖用户选择。
- 定向消息可追溯但不推进正式轮数或检查点。
- LLM 不可用时仍有固定选择卡和可用的策略模板。
- 刷新、跨恢复和完成态不可改写语义保持不变。
- 用户可在定向或选择卡阶段退出；“继续阅读报告”不产生隐式状态跳转。
- Golden Path 覆盖“未形成观点、拒绝挑战、选择不同动作、LLM 降级、选择卡阶段刷新恢复”。

## 协作方式

每张实现票开始前，用户提供目标场景、2–3 个理想对话样例和一个反例；Codex 据此维护 Issue 验收条件、实现和自动化验证。保持一个会触及状态机/Provider/数据库的主实现票；另一方并行准备下一票的内容、体验反馈与验收样例。只有文件边界明确时才并行代码票。
